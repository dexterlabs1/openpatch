# Twenty creative module contracts

Research/design checkpoint: 2026-10-17. **Tidal Functions is implemented with focused local Mac qualification; nineteen entries remain proposed.** This is an implementation backlog with explicit source and behavior boundaries, not twenty additions to the shipped catalog. The first [development candidate](TIDAL_FUNCTIONS.md) is not installed; family-level macOS CI remains pending. Keep installed OpenPatch 0.2.7 build 9 stable until an authorized upgrade.

## Scope and existing instruments

The intended outcome is twenty distinct patching capabilities, delivered in coherent families. New kinds retain independent identities, presets, history and import declarations. The current [`macro_voice`](MACRO_VOICE.md) already supplies eight engines; its FM/additive shaping uses Plaits-derived algorithms, but it is an original instrument rather than a Plaits port. The current [`modal_resonator`](MODAL_RESONATOR.md) is an original sixteen-mode mechanical model. Neither should be renamed and counted again.

Also already present: VCOs, wavetable oscillators, a drum voice, ADSRs/LFOs, random voltages, S&H/ASR, logic/process, mixers, quantizers, delay and reverb. Each proposal below states the behavior that makes it a new instrument. A new panel or additional preset is insufficient.

The reference firmware snapshot is [`pichenettes/eurorack` commit `f4cfa7697095a28d292bff758beb51deb49b5a86`](https://github.com/pichenettes/eurorack/tree/f4cfa7697095a28d292bff758beb51deb49b5a86), observed with `git ls-remote` on the research date. This pins a repository revision, **not a verified firmware release number**. Before adapting a module, record its exact files, resources, dependency revisions and per-file license headers. Upstream distinguishes STM32 MIT firmware, AVR GPL firmware and CC BY-SA hardware designs; preserve attribution and use independent OpenPatch names/panels. [Upstream licensing and derivative guidance](https://github.com/pichenettes/eurorack#license).

## First implementation family

Start with **Tidal Functions → Frame Scene → Segment Garden**, entries 1–3. They turn the existing voices into evolving, playable instruments without first adding another oscillator. The first vertical slice is Tidal Functions alone, then a saved modulation scene, then segment composition. Each needs real DSP, shared rack/browser controls and complete document/history behavior before the next is called done.

* Tidal Functions has an identifiable portable source kernel: [`tides2/poly_slope_generator.cc`](https://github.com/pichenettes/eurorack/blob/f4cfa7697095a28d292bff758beb51deb49b5a86/tides2/poly_slope_generator.cc), with MIT permission header inspected. Adapt the complete required ramp/shaper/resource paths; freeze a standalone C++ reference before changing their arithmetic.
* Frame Scene's [`frames/keyframer.cc`](https://github.com/pichenettes/eurorack/blob/f4cfa7697095a28d292bff758beb51deb49b5a86/frames/keyframer.cc) also has an inspected MIT header. This is a source adaptation of its control interpolation; its analog VCA/mix path needs a separately declared model. Do not call the entire hybrid hardware port source-identical.
* Segment Garden's [`stages/segment_generator.cc`](https://github.com/pichenettes/eurorack/blob/f4cfa7697095a28d292bff758beb51deb49b5a86/stages/segment_generator.cc) has an inspected MIT header. Group discovery, loop flags and transition order are part of the contract, not just an envelope curve.

Kinks/Links can be useful patch templates or later circuit studies, but are excluded from the twenty: their published directories contain analog hardware designs, not DSP firmware to port, and their bundled rectifier/min-max/S&H/buffer/mixer functions substantially overlap current modules. [Kinks reference](https://pichenettes.github.io/mutable-instruments-documentation/modules/kinks/), [upstream source layout](https://github.com/pichenettes/eurorack/tree/f4cfa7697095a28d292bff758beb51deb49b5a86/kinks/hardware_design).

## Source adaptation candidates: twelve contracts

“Port candidate” means a future implementation must preserve source behavior and prove its declared comparison domain. No comparison or hardware-fidelity claim exists yet. The family order below prioritizes playable modulation, then sound transformation, then larger voices.

| **1 Tidal Functions** `tidal_functions` | Clocked four-output AD/AR/cycling function generator. Reset/PLL behavior and patch-presence normalization must be explicit. | [Tides 2018](https://pichenettes.github.io/mutable-instruments-documentation/modules/tides_2018/), pinned `tides2/`; MIT source adaptation candidate; **first**. |

## Original designs informed by public manuals: eight contracts

These are **original OpenPatch instruments**, with original implementation under the project's MIT license. Make Noise manuals describe musical behavior; they do not provide a license to its firmware, schematics, artwork or exact transfer functions. No proprietary source was found or relied upon. Source availability has not been established, so none is called a Make Noise port. Reference names identify functional inspiration, not product branding or endorsement.

The version for each is the named hardware/manual edition retrieved on 2026-10-17; no unverified firmware number is assigned. Before implementation, archive the chosen PDF hash and page references. Firmware-specific later features stay excluded unless separately specified.

## Delivery and evidence gates

1. **Contract before catalog entry.** Specify every port, unit, voltage normalization, connection-sensitive behavior, mono/poly policy, reset/retrigger rule, sample-rate domain, bypass and state ownership. Begin source ports at the reference's channel count; arbitrary sixteen-voice wrapping is a later behavior extension with a CPU/memory budget. Model names remain honest: source-adapted digital, circuit-derived, physical or functional as applicable.
2. **Source reference before rewriting.** Vendor the pinned kernel/resources and required dependency commits with notices. Build an independent headless C++ reference harness at the original block/control rates. Test startup, boundaries, clock/trigger/repatch timing and feedback, not only a steady note. Preserve fixed-point arithmetic, PRNG draw order, tables and state transitions where relevant. Rate conversion around the kernel has its own latency/interpolation contract. Do not substitute a similar-sounding algorithm and retain a source-equivalence label.
3. **Hybrid paths need two proofs.** Frames/Streams firmware does not contain their entire analog audio chain. Compare the digital controller to source and validate the separately specified analog model numerically. Original analog-inspired designs need equations, stability/energy/response tests and evidence appropriate to their model; hardware accuracy requires measurements or a defensible circuit reference beyond public controls.
4. **Host integration is part of done.** Compile/process/restore without callback allocation, deallocation, locks or filesystem work; bounded memory and denormal/nonfinite handling; exact document/preset/history/MCP authority; prepared sample/keyframe/scale assets published off the audio thread. Freeze buffers/long recording history only under a declared bounded persistence policy. Never silently discard a reel, keyframe or learned scale.
5. **One musical demonstration per family.** First family: a four-phase modulation patch and a recalled scene modulating the existing Macro Voice/Modal Resonator. Later families: a looping generative percussion patch, a stereo live-texture instrument, and an excited-string performance. Shared rack/browser panels, readable meaningful controls and restrained light are required. Original OpenPatch instruments appear in both Custom and their functional categories. An attractive capture alone is not DSP qualification.
6. **Count only completed instruments.** A family is implemented after relevant DSP/reference, lifecycle, allocation and UI checks pass; macOS ARM milestone CI remains the release gate. Record implemented, validated and installed separately. The user has authorized combined GPL source usage; integrate the AVR candidates with their actual notices, corresponding source and combined-distribution licensing obligations. Do not label imported GPL code or map tables MIT. Completing this document creates zero catalog kinds and establishes no new VCV or physical-hardware compatibility.
